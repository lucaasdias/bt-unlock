# BT Unlock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship an installable webOS app that lets the owner of a rooted LG
webOS TV pair, connect, and manage any Bluetooth accessory (game
controllers, keyboards, mice, headphones/speakers) that the stock LG UI
blocks — no SSH, no computer, in Brazilian Portuguese, English, and other
major languages.

**Architecture:** A plain-JS webOS web app (no framework) that never talks
to the Bluetooth Luna API directly. Every privileged call is a small root
shell script, invoked through Homebrew Channel's already-elevated
`luna://org.webosbrew.hbchannel.service/exec`, which returns the script's
stdout. The UI is three screens (adapter status, discover & pair, paired
devices) sharing one small router, with device-list polling in place of a
live subscription (verified necessary and sufficient during design: `exec`
is a single blocking call, and `luna-send -n N` already blocks until it
has collected its N replies, so multi-reply flows — pairing's passkey
exchange included — are handled entirely inside the shell script, never
in JS).

**Tech Stack:** webOS web app (HTML/CSS/vanilla JS, no framework),
`@webos-tools/cli` for packaging (`@webosose/ares-cli` is known broken on
current Node — confirmed when we hit it installing Kodi), POSIX `sh`
scripts for every root-privileged operation, Node's built-in test runner
(`node --test`) for the pure-JS logic that doesn't touch the Luna bus.

**Spec:** [`docs/superpowers/specs/2026-10-20-bt-unlock-design.md`](../specs/2026-10-20-bt-unlock-design.md)

## Global Constraints

- webOS 4.0+ is the supported floor; no React or comparable framework.
- Every privileged operation goes through `luna://org.webosbrew.hbchannel.service/exec`, never through the app's own elevated service.
- A startup script lives at `/var/lib/webosbrew/init.d/` as a **symlink**, not a copy; it checks its target exists and stops if not; it writes what it did under `/var/lib/webosbrew/`.
- UI strings ship in at least Brazilian Portuguese (`pt-BR`) and English (`en`, required fallback), with other major languages added once the string set is final.
- No app partition write outside `/var/lib/webosbrew/` and `/tmp`; never touch a system (squashfs) partition.
- Source repo: `github.com/lucaasdias/bt-unlock`, public, MIT or GPLv3 — **not pushed until the human partner says the TV testing is done** (explicit instruction; Task 9 is the only task that touches GitHub).

## Review Focus

- **A device the user cancels pairing on, or that times out mid-pair** (e.g. walks away, battery dies): the UI must leave the status screen in a clean, re-triable state, not stuck on a spinner forever. Task 5.
- **A device whose class-of-device doesn't map to HID or A2DP** (e.g. a phone, a printer): the app must show it as unsupported rather than attempt a profile connect that will fail silently. Task 3 and Task 5.
- **The adapter already off when the user opens Discover**, or turned off by someone else mid-session: Discover must detect this and prompt to power on rather than show an empty, unexplained list. Task 4 and Task 5.
- **`exec`'s own failure modes** — Homebrew Channel not installed, root status not `ok`, or the call itself erroring (`returnValue: false`): every screen must show this as a distinct, understandable error state, not a blank screen (this is the exact failure class diagnosed in `webOS Terminal` on this TV). Task 2.
- **Forgetting a device that's currently connected**: must disconnect first, then unpair, not leave a dangling HID/A2DP connection the OS still thinks is active. Task 6.

### Task 2: `luna.js` — the exec() wrapper, and the root-script convention

**Files:**
- Create: `js/luna.js`, `scripts/bt-common.sh`
- Test: `test/luna.test.js`

**Interfaces:**
- Produces:
  - `exec(scriptName: string, args: string[]) -> Promise<{ ok: boolean, replies: object[], errorText?: string }>` in `js/luna.js` — every later screen calls this and nothing else to reach a root script.
  - `scripts/bt-common.sh` sourced by every other script in `scripts/`, providing a `run_luna <uri> <json>` shell function that prints one line of JSON per reply (NDJSON) and a `log <message>` function that appends to `/var/lib/webosbrew/bt-unlock.log`.

- [ ] **Step 1: Write `scripts/bt-common.sh`**

`run_luna` wraps `luna-send -n "$2" -f "$1" "$3"` (where `$2` is a reply
count, default `1`), printing each JSON reply on its own line with no
extra framing — this is what makes the output NDJSON and parseable by
`exec()` without a custom protocol. `log` prefixes each line with an
ISO-8601 timestamp.

- [ ] **Step 2: Write the failing test for `luna.js`'s reply parser**

```js
// test/luna.test.js
test('parseReplies splits NDJSON stdout into objects', () => {
  const stdout = '{"returnValue":true,"a":1}\n{"returnValue":true,"a":2}\n';
  assert.deepStrictEqual(parseReplies(stdout), [{returnValue:true,a:1},{returnValue:true,a:2}]);
});

test('parseReplies surfaces a returnValue:false reply as the ok:false case', () => {
  const stdout = '{"returnValue":false,"errorText":"boom"}\n';
  const result = toExecResult(parseReplies(stdout));
  assert.strictEqual(result.ok, false);
  assert.strictEqual(result.errorText, 'boom');
});
```

- [ ] **Step 3: Run the tests to verify they fail**

Run: `node --test test/luna.test.js`
Expected: FAIL — `parseReplies is not defined`.

- [ ] **Step 4: Implement `parseReplies(stdout: string) -> object[]` and `toExecResult(replies: object[]) -> {ok, replies, errorText?}` in `js/luna.js`**

`parseReplies` splits on newlines, drops empty lines, `JSON.parse`s each.
`toExecResult` returns `ok:false` with the last reply's `errorText` if
any reply has `returnValue:false`; otherwise `ok:true`.

- [ ] **Step 5: Implement `exec(scriptName, args)` in `js/luna.js`**

Calls `luna://org.webosbrew.hbchannel.service/exec` (via
`window.PalmSystem`/`webOS.service.request`, matching the pattern
confirmed live on the TV in this session) with
`{"command": "sh /media/developer/apps/usr/palm/applications/<appId>/scripts/<scriptName> <args joined and shell-escaped>"}`,
then runs the response's `stdoutString` through `parseReplies` and
`toExecResult`. If the `exec` call itself returns `returnValue:false`
(Homebrew Channel not elevated, etc.), return
`{ok:false, errorText: <that reply's errorText>}` without attempting to
parse `stdoutString`.

- [ ] **Step 6: Run the tests to verify they pass**

Run: `node --test test/luna.test.js`
Expected: PASS

- [ ] **Step 7: Manual on-TV smoke test**

From the app (add a temporary debug button, or via `ares-shell`), call

`ok:true` comes back with the `id` script's real output, matching the

### Task 5: Screen 2 — Discover & pair

**Files:**
- Create: `scripts/bt-discover.sh`, `scripts/bt-pair.sh`, `scripts/bt-connect.sh`, `js/screens/discover.js`
- Modify: `js/router.js` (add the Discover route), `js/app.js`

**Interfaces:**
- Consumes: `exec()` (Task 2), `classify()` (Task 3), `isAdapterPowered()` (Task 4).
- Produces: nothing later tasks depend on directly; this is a leaf screen.

- [ ] **Step 1: Write `scripts/bt-discover.sh`**

One subcommand: `start` runs
`run_luna luna://com.webos.service.bluetooth2/adapter/startDiscovery 1 '{}'`,
then `run_luna luna://com.webos.service.bluetooth2/device/getStatus 1 '{}'`
(a single, non-subscribed snapshot — this is the poll primitive; the UI
calls `exec('bt-discover.sh', ['start'])` once, then calls it again
every ~2s on a timer to refresh the list, matching the polling decision
made in the spec).

- [ ] **Step 2: Write `scripts/bt-pair.sh`**

Takes the target address as `$1`. Runs
`run_luna luna://com.webos.service.bluetooth2/adapter/pair 3 '{"address":"'"$1"'","subscribe":true}'`
— `3` replies covers `{subscribed:true}`, then either the passkey-request
event or the final pairing result; it's the shell's `luna-send -n 3`
blocking until it has them, per the architecture's core decision, so the
JS side gets back a complete NDJSON transcript in one `exec()` round
trip. If the middle reply is a `request:enterPasskey` event, the script
has nothing to act on — surfacing that to the user and resubmitting a
passkey is Task 5's known deferred case, see Step 6 below.

- [ ] **Step 3: Write `scripts/bt-connect.sh`**

Takes address and profile (`hid` or `a2dp`) as `$1`/`$2`, runs
`run_luna luna://com.webos.service.bluetooth2/<profile>/connect 1 '{"address":"'"$1"'"}'`.

- [ ] **Step 4: Write `js/screens/discover.js`**

`render(container)`: if `isAdapterPowered()` is false, shows a prompt to
go power it on (links back to the status screen) instead of scanning.
Otherwise starts polling `bt-discover.sh start`, rendering each device
with `classify(device.classOfDevice)`'s icon and kind, skipping entries
where `profile` is `null` (the "unsupported, don't offer it" case from
the spec's non-goals). Selecting a device calls `bt-pair.sh` then, on
success, `bt-connect.sh` with the classified profile; shows a clear error
state (not a stuck spinner) if either step's `ok` is `false`, or if
discovery itself failed because the adapter turned out to be off anyway
(race with another client disabling it mid-session — the exact case from
Review Focus).

- [ ] **Step 5: Manual on-TV test**

Using the already-paired-in-this-session DualShock 4 as the known-good
case: unpair it by hand first (`luna-send` over SSH, or wait for Task 6),
then pair it again through the Discover screen UI and confirm it shows
up as a gamepad, pairs, and connects without the app needing SSH.

- [ ] **Step 6: Document the passkey-entry gap and commit**

The `enterPasskey` mid-pairing case (a device that isn't Just-Works) has
no UI yet — add a one-line `// TODO` in `discover.js` at the spot the
error state is rendered, and list it explicitly as not-yet-tested in the
plan's final self-review note (see below) rather than silently shipping
it as "done."

